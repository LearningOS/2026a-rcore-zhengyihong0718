## 实现与边界

在 ProcessControlBlockInner 保存默认关闭的开关。sys_enable_deadlock_detect 只接受 0、1，其他参数返回 -1 且不改变原状态。新进程和 fork 子进程按本框架重新建立空同步对象表及关闭状态，父子进程不共享检测状态。

每个同步对象保存 Available、按 tid 索引的 Allocation、按 tid 索引的 Need。检测前复制同类资源的快照，添加当前一次请求，再按官方算法反复寻找 Need 不超过 Work 的线程，模拟其完成并将 Allocation 加回 Work。全部线程可消除才允许请求。该算法检测当前已提出的请求，不要求线程提前声明未来最大需求。单次消除计算最坏约 O(n²m)，使用有序映射还包含键查找开销；适合本章小规模教学进程，没有实现大规模增量检测。

拒绝操作只作用于快照，不减少真实可用量，也不进入真实等待队列。互斥锁和信号量分别检测，符合题目允许的简化；未检测两类资源之间、条件变量或 waittid 共同形成的混合死锁。

MutexSpin 的未获锁请求在让出 CPU 时保留 Need，真正拿到锁才计入 Allocation。MutexBlocking 的 unlock 保持原有直接交接语义，唤醒前就将资源记给等待线程，而不是等其再次运行后才更新。Semaphore 的负 count 表示等待者数，不能直接用作 Available；up 唤醒时同步完成交接，down 恢复后不重复计数。条件变量内部的 mutex.unlock/lock 同样更新原语状态，避免仅在系统调用包装层记账而遗漏。

线程退出时，先结束 TCB 内部借用，再从检测数据移除该 tid 的持有及需求条目；不增加 Available。这样已退出线程不能被算法当作仍会运行并释放资源的线程，回收的 tid 也不会继承其记录。普通锁不具备健壮锁的自动恢复语义，持锁退出不会自动解锁；信号量允许无持有单位的生产者执行 up。这里没有把 post 限制为只能由原 down 线程执行。

本章按官方说明直接基于 ch8 框架，仅迁移此前 get_time，不整体合并旧章节内核。时间 ABI 为两个 usize；先验证全部目标字节的地址、有效用户映射和写权限，再独立翻译并写入各字节，因此可跨不连续物理页，失败时不会留下部分输出。

## 问答一：主线程退出时回收什么，TCB 在哪里被引用？

需要终止进程内全部线程，回收各线程用户栈、trap context 对应页及 tid，释放程序代码、数据、堆等地址空间页面与页表，关闭文件描述符并释放其 Arc；随后清除线程表及同步对象等进程资源。内核栈随 TCB 的最后强引用释放，不能在仍使用该栈执行退出路径时立即回收。PCB 先保留僵尸状态、退出码及必要标识，供父进程 waitpid 收集；子进程转交 INITPROC，不能因父进程退出直接当作普通内存删除。

本框架中 TCB 的引用主要有以下几处：

1. Processor.current 是运行线程的强引用。退出先 take_current_task，脱离调度器的当前任务槽。
2. PCB.tasks 保存线程强引用。其他线程的用户资源先 take 到临时集合，释放 PCB 借用后再销毁，避免 TaskUserRes 析构再次借用 PCB 导致冲突；最后清空 tasks。
3. TaskManager.ready_queue 保存就绪线程强引用，必须显式移除，否则进程退出后线程还可能被调度。定时器等待队列也持有强引用，必须取消，否则未来超时会重新唤醒已失效线程。代码中的 remove_inactive_task 同时处理这两处。
4. 阻塞 Mutex、Semaphore、Condvar 的等待队列持有 TCB 强引用。这些对象属于进程，进程与同步对象释放时也必须释放队列中的引用；不能仅清空就绪队列就认定所有 TCB 已析构。当前退出代码依赖 PCB 及同步对象的后续析构处理这些队列，没有逐一取消所有同步等待。若挂起调用另持有对象 Arc，需要额外审计其生命周期，不能把逻辑终止等同于已验证的全部物理内存回收。
5. TaskManager.stop_task 临时保留退出主线程，保证切换离开旧内核栈前栈仍然存活；以后安全替换该引用再释放。其他线程退出后，其 TCB 也保留在 tasks 中供 waittid 读取退出码，然后再移除。

TCB.process 是 Weak，单独这一条不会保持 PCB 存活。但其他强引用和挂起内核调用的局部变量仍须按实际所有权图检查。本实验新增的检测条目只保存 tid 和整数，不额外持有 TCB/PCB 的 Arc。

## 问答二：两种 Mutex 实现的区别与问题

Mutex1 在 unlock 时先设置 locked=false，再唤醒等待者。被唤醒线程恢复后重新进入循环检查和竞争，因而不把唤醒等同于取得锁。新的运行线程可以在等待者再次被调度前抢先拿锁，即插队；在持续竞争下，较早等待的线程可能反复被唤醒又阻塞，产生额外调度甚至饥饿。循环重查保证这种插队不会让两个线程同时进入临界区。

Mutex2 有等待者时不清除 locked，而是把锁的持有权直接交给队首。等待者从 block 返回后直接结束 lock，无需重新竞争；后来者仍看到 locked=true，会排在队列后面。在本章无任意虚假唤醒、取消和超时的假设下，这减少插队与反复阻塞，并让队列内交接保持先进先出。它仍依赖调度器最终运行获得锁的线程，不是对任意调度的等待时间保证。

二者的 lock 与 unlock 必须配套。若使用 Mutex1 的解锁清零方式，却使用 Mutex2 不重查的获取方式，新线程抢锁后旧等待者也会直接进入临界区，破坏互斥。反之，若使用 Mutex2 保持 locked 的交接方式，却让被交接者像 Mutex1 那样继续检查，则它看到 locked=true 会把自己再次阻塞，造成锁无人继续释放的死锁。若扩展虚假唤醒、取消或等待超时，也须增加明确的拥有者或交接状态，不能直接沿用一次阻塞后必然持锁的假设。
